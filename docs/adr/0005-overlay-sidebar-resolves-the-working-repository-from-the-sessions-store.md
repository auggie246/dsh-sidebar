# The overlay Sidebar resolves the Working Repository from the sessions store, not from a framework sessionId

Ticket #14: on a new (blank) session the Source Control and Commit Graph cards resolve no Working Repository — every git call runs against the deployment root and reports "not a git repository". The verified platform chain: before the first message the session-scoped `details` slot cannot host the Sidebar. The layout declares `details` with `scope: "session"` and hard-zeros its column until the current session has `blank === false` (the `detailsSession` selector feeding `computeColumns(..., detailsSession === void 0 ? 0 : panels.details)` in `@deepseek-ai/dsh-client-ui-layout`'s client). So the open Sidebar floats on `shell.overlay` instead — declared `scope: "root"` in the same registration, rendered by AppFrame with empty owner props (`renderSlot("shell.overlay", {})`). Root-scope entries receive exactly the standard props `{ useSessions, useWorkspaces }`: `sessionId` is assigned only in the session/session-maybe branches, from `info.sessionId` (`standard["sessionId"] = info.sessionId` in `@deepseek-ai/dsh-client-ui-renderer`'s client, where the root branch returns the two-hook cache and `RootEntry` passes `void 0`). Overlay-mounted, `SidebarPanel` therefore has no `sessionId`; its empty `cwd` hits the host half's `cwdOf` fallback (`sandboxPolicy.workspaceRoot`), and `git -C '<deployment root>'` fails — git treats an empty `-C` as a no-op resolving to the process cwd (verified on git 2.55.0), and a deployment root is generally not a repository, so every probe exits 128 with git's "fatal: not a git repository".

We decided the overlay Sidebar resolves the Working Repository from the root-scope standard props themselves — the sessions store's current session matched against the workspaces snapshot — rather than waiting on a framework `sessionId` that only exists in session scope. The Rail already subscribes to `useSessions`; it hands the current session id (`s.current`) to `SidebarPanel`, whose existing `useWorkspaces` match (the workspace whose `sessionIds` contains that id, per `WorkspaceListState`/`WorkspaceView` — `items[].path` and `items[].sessionIds`) yields the path. The match is sound because workspace accounting is immediate on the host: `session.create` with a `workspaceId` attaches the session to the workspace before the RPC responds (`workspace.attachSession` prepends the id to the record's `sessionIds` in `@deepseek-ai/dsh-workspace`), and the client's projected snapshot receives the updated workspace view through the `host/workspace-changed` frame (`@deepseek-ai/dsh-client-runtime`'s `handleHostEnvelope` → `upsert`). The New Session flow itself targets a workspace by exactly this account (`startSession` finds the workspace whose `sessionIds` includes the current session; `connectWorkspace` reuses or creates its blank session). Both stores are observable snapshots, so the match lands reactively once the accounting frame arrives — no polling. Note the sessions store alone cannot resolve the path: the summary it merges on `session.create` carries no `cwd` when the session was created through a workspace, which is exactly why this decision is a two-store join and not "read the cwd off the current session".

Rejected alternatives. Moving the Sidebar out of the session-scoped `details` slot into a root-scoped slot so a framework `sessionId` is never needed: root scope never carries `sessionId` (verified above), so it fixes nothing, and it would discard ADR 0003's active-versus-started split and the reserved-width overlay behavior — docking depends on session scope. Teaching the host half to fall back to a "current workspace" concept: the host sees no session context on the Sidebar's plugin shell calls, and guessing a workspace below the deployment root would run git against an arbitrary repository — the deployment-root fallback is exactly the failure mode being fixed, and a wrong-but-plausible `cwd` is worse than the visible "not a git repository" empty state.

Consequence: a blank session created by the New Session flow now shows live Source Control and Commit Graph for the workspace it landed in, before its first message. Resolution stays in one place — the same `useWorkspaces` match the details path already uses — so the overlay and docked Sidebar cannot disagree. A session created without a workspace (or attached to none) still falls through to the deployment root and renders the empty state; that is the contract working as designed, not a residual bug. If DSH later exposes a session id at root scope, the Rail's hand-off can shrink to a fallback, but the sessions store remains the authority for every root-rendered surface.

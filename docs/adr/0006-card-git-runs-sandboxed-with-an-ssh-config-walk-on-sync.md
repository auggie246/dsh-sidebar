# Card git runs sandboxed through the shell service; sync walks the ssh config only after ssh's exact ownership error

Tickets #13 and #17. The Source Control card's git actions are human button clicks, yet every spawn is confined — a future reader will wonder why a human-facing surface pays a sandbox tax and why sync carries an ssh config walk. The verified platform chain: the host half is in-process Cordis plugin code inside the `dsh web` process, and DSH gives plugins exactly one sanctioned way to spawn processes — the `shell` service, whose executor resolves every command against the deployment sandbox policy (default `read-only`) or a per-call policy the caller supplies. There is no unsandboxed programmatic spawn path for plugins. So the card stamps `sandboxPolicy: { mode: 'workspace-write', workspaceRoot: <Working Repository> }` on every git call (#13): the human click is the approval, the repository is the bound, and the sandbox exists to bound installed plugin code — installable from npm or GitHub — not to confine the agent. Two further verified platform facts make sync special: the sandbox masks metadata for paths outside the workspace (`stat` on `/etc/ssh/ssh_config.d/20-omarchy-keepalive.conf` reports `nobody:nobody`; `$HOME/.ssh/config` reports its real owner), and ssh refuses to read any config file it cannot ownership-check — so on ssh remotes every sync died with "Bad owner or permissions on /etc/ssh/ssh_config.d/*.conf" before any network access, while the user's own terminal (no sandbox) kept working.

We decided to keep the sandboxed shell-service path for sync and to retry, not to seek an unsandboxed door. When a sync attempt fails with ssh's exact `Bad owner or permissions` or `Can't open user config file` error, the host walks `core.sshCommand` the same chain a human would: first `ssh -F ~/.ssh/config` — the file the sandbox does not mask, so host aliases, ports and IdentityFile settings still apply — then `ssh -F /dev/null`, whose default identity-file probing (`id_ed25519`, `id_ecdsa`, `id_rsa`, …) and agent need no hard-coded key name. No key path is ever written into the plugin: a user with a custom-named key and a config works at the first retry, a user with a default-named key and no config works at the second, and the last attempt's error is what surfaces to the card.

Rejected alternatives. Running sync through the `subprocess` PTY service (the seam the Terminal tab uses, which is not sandboxed): PTY output scraping yields no exit codes and no clean stderr, so action errors — which the card must keep on screen per #13's companion fix — would be guesses. Bypassing ssh's config unconditionally on every sync: it would change behavior on healthy machines whose users rely on their ssh config, for a failure that only exists under masking. Fixing the system file (`sudo chown`, permission edits): the file is genuinely `root:root 644`; masking is the cause, so touching the system treats the wrong patient. Asking DSH for a user-consented unsandboxed escape for user-initiated plugin spawns, or for masking to leave real ownership metadata on system paths: both are the clean upstream fixes and should be proposed there; neither exists today, so the walk is the narrowest seam available from inside the plugin.

Consequence: healthy machines and non-ssh remotes never reach the walk — behavior is byte-for-byte the pre-#17 path. A masking machine self-heals within one retry on the exact error. A hypothetical DSH build that masks `$HOME` too still lands on the config-free step. If DSH later fixes masking or ships a consented unsandboxed escape, the walk can shrink back to the plain attempt — the test (`scripts/test-sync-ssh-retry.mjs`) pins each step of the chain so that shrink is a deliberate change, not an accident.

# The Explorer Card opens preview tabs through a pending-open store drained by the Panel

The Explorer Card is the first Card that is not git-bound and the first Card that asks the Panel to do something: selecting a file in its tree opens a read-only preview Panel Tab. Until now no seam linked a Card to the Panel — Panel Tabs were created only inside `BottomPanel`'s own "+" picker (`createTab({ id, type, path })` in the picker branch of `lib/client.js`), and `BottomPanel` mounts only from the Rail when the Panel is open, is keyed by session id, and holds its tab list in local state seeded from `dsh.rsidebar.panels.v1.<sessionId>` and re-read on every remount (ADR 0003, ticket #6). Three properties follow that a naive design breaks: the Card cannot own tab state (hidden Cards are unmounted by the Card Manifest's visibility filter, so card-owned state would silently lose pending opens); the open request must survive `panelOpen === false` (a closed Panel unmounts `BottomPanel`, so no listener inside it can be assumed present at click time); and the click must not depend on a framework `sessionId` (ADR 0005 shows the overlay Sidebar renders at root scope with no session id at all).

We decided on a module-scope pending-open store in the client half: the Explorer Card enqueues an open request for the current session's workspace path, the Rail's existing panel-open control flips the Panel open, and a mounted `BottomPanel` drains the store — creating one tab per file path, deduplicating so a repeated click focuses the already-open tab instead of duplicating it, and persisting through the same `dsh.rsidebar.panels.v1.<sessionId>` mechanism the "+" picker already uses. The store is the whole seam: the Card never imports Panel internals, the Panel never knows the Card exists, and both keep working when the other is absent — a click with no mounted Panel leaves a pending request that the next mount drains.

Rejected alternatives. Lifting tab state out of `BottomPanel` into the Rail: this rewrites the per-session, re-read-on-remount contract that ticket #6 pinned and every Panel Tab test asserts; the bug that contract fixed (tabs leaking or dying on Panel close/reopen and session switch) is exactly the failure a lift would reintroduce. Coordinating through the host half: ADR 0002 records that host→client has no push channel and the event allowlist is closed, so a host round trip buys an RPC for what is purely client-side coordination between two components in the same bundle. Rendering the preview inside the Explorer Card itself: rejected at design time — the Card column is narrower than the Panel, the existing `FilePreviewTab` rendering would be duplicated, and it would conflate two regions the glossary deliberately keeps independent (Sidebar and Panel each have their own toggle and remembered size).

Consequences. This is the first cross-region seam beyond the Card Manifest; any future Card that wants the Panel to open something (a diff viewer, a log tail) reuses the same store rather than inventing a second channel, so the store — not the Explorer — is the API to keep stable. The drain must be idempotent across `BottomPanel` remounts (the keyed remount is by design), which the dedupe-by-path rule gives for free. Tab identity stays path-scoped per session, so the explorer's "one tab per file, repeat click focuses" rule and the picker's tabs share one model — closing a preview tab closes the file, and reopening the file is just another click. If DSH later adds a sanctioned cross-component bus for plugin regions, this store is the one place that migrates.

# The Panel button is live once a session exists, not once the first message is sent

Ticket #5 gated the Panel on the same condition the Sidebar toggle uses: the Rail button stayed disabled until the current session had `blank === false` — that is, until its first message was sent — and the region stayed unmounted with it. Living with the gate showed the wrong line was drawn. A fresh session is a real session: it has an id, it hosts Panel Tabs under `dsh.rsidebar.panels.v1.<sessionId>` (ticket #6), and its first act is often opening a terminal — which is exactly what the gate forbade. The `.rsb-rail button:disabled` opacity then read as breakage, not as intent.

We decided to split the two conditions the old gate conflated. `activeSessionId` (any current session, blank or started) now drives the Panel button and the `BottomPanel` mount. `startedSessionId` (first message sent) keeps only the jobs it was right for: the Details Column open/close effect and the overlay-versus-docked Sidebar choice. With no session at all, the button stays disabled and titled "Panel opens once a session exists". Rejected alternative: auto-opening the Panel on session creation — that would fight the user's stored `panelOpen` preference and the ticket #1 baseline.

Consequence: a blank session can host a terminal and every other Panel Tab type before its first message. The stored `panelOpen` preference now takes effect the moment a session exists, which also removes the "restored Panel stays hidden" asymmetry the old gate produced. The Panel keeps its per-session key, so a session start never remounts or re-reads another session's tabs.
